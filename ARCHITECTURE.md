# Ledger — Technical Architecture Assessment

**Date:** 2026-07-28  
**Scope:** Full codebase analysis  
**Purpose:** Guide future AI contributors to make safe, informed changes  

---

## Executive Summary

Ledger is an offline-first personal finance PWA built without frameworks or build tools. It uses vanilla JavaScript with an IIFE-based module pattern, a single monolithic CSS file, and IndexedDB + localStorage for persistence.

The architecture is **service-oriented in intent but mixed in practice**. A `store.js` file centralizes CRUD mutations for all entities (transactions, accounts, categories, people, groups, recurring, debt items), but validation, category suggestion, reconciliation logic, and import processing live in UI modal files and service files with no formal boundary between layers.

The application is **moderately maintainable** for a solo developer but **risky for multiple AI contributors** due to:

- Duplicate filtering logic across pages
- Business rules embedded in modal UI code
- Side-effect-heavy mutation functions
- No test coverage for most critical paths

**Overall Health:** Functional — many edge cases are handled. But the architecture makes it easy to introduce regressions.

---

## Strengths

### 1. Single-file store mutation layer

`store.js` provides `addTransaction`, `updateTransaction`, `deleteTransaction`, `addTransactionBatch`, `upsertTransaction`, and `deleteTransactionsByLink`. Every path that writes to `DB.transactions` should go through one of these. (The one known bypass is in `wire/transactions.js` bulk delete.)

### 2. Consistent module pattern

Every file uses an IIFE that attaches to `window.Ledger`. No globals leak. Script load order in `index.html` defines the dependency graph explicitly.

### 3. Offline-first by design

`storage.js` implements IndexedDB with automatic localStorage fallback. On boot, IDB is checked first; if empty, localStorage is migrated. Every `saveData()` call writes to both.

### 4. Good cross-currency transfer handling

`commitLinkedTransferPair` creates two linked rows (expense out, income in) sharing a `linkId`. This is correct — each account sees the transaction in its own currency.

### 5. Category auto-learning

The learning system (`learnCategory` / `learnSubcategory` / `suggestCategoryForDescription`) is modular. It lives in `constants.js` with no UI dependency, accepts DB as a parameter, and has a clear scoring pipeline.

### 6. Responsive modal system

`modals.js` implements append-based stacking with focus trapping, Escape-to-close, backdrop click-to-close, and focus restoration on close. Sub-modals stack correctly.

### 7. Reconciliation drift detection

`needsVerification()` checks if an account was reconciled this month. `accountBreakdown()` provides a full transaction-level breakdown for debugging balance mismatches.

## Weaknesses

### 1. Business logic embedded in UI

`modals/tx-modals.js` contains:
- Amount/date/from-to validation
- Cross-currency transfer pair logic
- Category and subcategory learning calls
- Friend split debt item creation
- Refund linking logic
- Category split construction

All of this lives inside `openTxModal()`, not in a service. Any new entry point (API, batch import) must duplicate or reverse-engineer this logic.

**Impact:** High  
**Priority:** Medium

### 2. Duplicated transaction filtering

`pages/register.js` `filteredTransactions()` and `pages/reports.js` `reportFilterTx()` are ~90% identical — same filter chain (type, account, currency, category, subcategory, date preset, search). Overview also has its own `overviewMatchDate()`.

**Impact:** Medium — filters are stable, but any change must be applied in 2-3 places.

### 3. Duplicated running balance computation

`utils.js` `accountBalance()` and `register.js` inline running balance loop are near-identical. The register inline version has no helper reuse.

**Impact:** Low — stable logic, unlikely to change independently.

### 4. Bulk delete bypasses deleteTransaction()

`wire/transactions.js` bulk delete:
```js
window.Ledger.DB.transactions = window.Ledger.DB.transactions.filter(function(x){ return x.id !== id; });
window.Ledger.replaceDebtItemsForTransaction(id, [], true);
window.Ledger.saveData();
```
This bypasses `deleteTransaction()` which does the same work. If cleanup logic is added to `deleteTransaction()` (e.g., removing links), bulk delete will miss it.

**Impact:** Medium  
**Priority:** High

### 5. Auto-posting recurring bypasses addTransaction()

`services/recurring.js` pushes directly to `DB.transactions` instead of calling `addTransaction()`. Skips any validation or side-effects that `addTransaction()` might acquire.

**Impact:** Medium — recurring items are generated by the system, so validation is less critical. Still a consistency risk.

### 6. Import preview has inline duplicate key that differs from utils

`import-preview.js` generates duplicate keys without `type` and `account` fields, while `utils.js` `_dupeKey()` includes them. This means the import preview's duplicate detection is slightly less accurate.

**Impact:** Low

### 7. No test coverage for critical paths

The `tests/` directory exists with `vitest.config.js`, but the project has no tests for:
- `commitLinkedTransferPair`
- `filteredTransactions` / `reportFilterTx`
- `accountBalance` / `accountBreakdown`
- Category suggestion ranking
- CSV import parsing
- Recurring auto-post logic

**Impact:** High — every change is a regression risk.

### 8. Side-effect-heavy mutations

Every `store.js` mutation calls `saveData()` + `renderPage()`. This means:
- Batch operations save/re-render per item in a loop
- Importing 100 transactions generates 100 saves
- Tests are difficult because every mutation re-renders the UI

## Technical Debt Register

| # | Description | Priority | Impact | Recommendation |
|---|---|---|---|---|
| TD-01 | Bulk delete in `wire/transactions.js` bypasses `deleteTransaction()` | High | Future cleanup logic added to `deleteTransaction()` will be missed by bulk delete | Replace bulk delete with a loop calling `deleteTransaction()` |
| TD-02 | Auto-post in `services/recurring.js` bypasses `addTransaction()` | Medium | Validation/side-effects added to `addTransaction()` are skipped | Route through `addTransaction()` |
| TD-03 | No test coverage | High | Every change is a blind regression risk | Add tests for: filtering, balance calc, transfer pair, CSV parsing, category suggestion |
| TD-04 | Duplicate `filteredTransactions` and `reportFilterTx` | Medium | Filter changes must be applied in two places | Extract shared filter logic into `utils.js` |
| TD-05 | `saveData()` + `renderPage()` called inside every mutation | Medium | Batch operations are slow, tests impossible | Accept for now — refactor only if batch import performance becomes an issue |
| TD-06 | Import preview duplicate key differs from `_dupeKey` | Low | Import may miss or falsely flag duplicates | Align key generation with `utils.js` |
| TD-07 | `normalizeDate` in csv-import.js has no tests | Medium | Date parsing bugs cause silent import failures | Add tests for all supported formats |
| TD-08 | Service worker cache must be manually bumped on every deploy | Low | Stale JS/CSS served to returning users | Could auto-version via build step, but project has no build step |

## Protected Modules

These modules require extra care before modification. Changing them risks breaking many downstream consumers.

### 1. `js/store.js` (CRITICAL)

**Why:** Every mutation function saves and re-renders. Every entity depends on these functions. The `DB` object is referenced by every module in the application.

**Risks:**
- Changing `saveData()` behavior affects all writes
- Adding a new required field to mutation functions breaks all callers
- Changing `renderPage()` invocation affects every page

**Testing required:** Full manual walkthrough of all CRUD paths.

### 2. `js/modals/tx-modals.js` (CRITICAL)

**Why:** Contains the most complex business logic in the app — validation, cross-currency transfer pairs, friend split debt creation, refund linking, category learning, category splits. 687 lines of intertwined UI + logic.

**Risks:**
- Moving validation into a service must match existing behavior exactly
- The `commitTransaction` → `upsertTransaction` chain is trivial but called from multiple branches
- `commitLinkedTransferPair` deletes existing links and re-creates — any logic error can lose data

**Testing required:** Create, edit, delete each type (expense, income, transfer, refund) with splits, cross-currency, friend splits, refund linking.

### 3. `js/services/import-preview.js` (HIGH)

**Why:** The unified import preview handles CSV import, statement paste, and category suggestion. It builds transaction objects, detects duplicates, groups by description, and commits via `addTransactionBatch`. Modifications risk breaking the entire import pipeline.

**Risks:**
- Category suggestion logic differs slightly from `tx-modals.js` — aligning them must produce identical results
- Duplicate detection uses a different key than `utils.js` — changing either affects what's flagged as duplicate

### 4. `js/utils.js` (HIGH)

**Why:** Contains `accountBalance`, `accountBreakdown`, `findDuplicates`, `findAllDuplicates`, `findOrphanTransfers` — all used by pages, modals, and services. These are read-only queries but critical for correctness.

**Risks:**
- Changing `accountBalance` logic affects every balance display in the app
- Changing `_dupeKey` affects duplicate detection everywhere

### 5. `js/modals.js` (HIGH)

**Why:** The modal system's open/close/focus-trap/Escape logic. Every modal in the app depends on this. Regression here breaks all pop-ups.

**Risks:**
- Focus trap changes affect accessibility
- Stack management changes affect sub-modal behavior
- Escape handler changes affect custom dropdown interaction

### 6. `js/constants.js` (MEDIUM)

**Why:** The category suggestion engine and keyword list. Used by the modal, import preview, and auto-categorize. Changes to the scoring algorithm affect all three consumers.

### 7. `js/pages/register.js` (MEDIUM)

**Why:** The core transaction listing page. `filteredTransactions` is used by the wire layer for bulk operations. Running balance computation affects displayed column data.

## Application Architecture

### Data Flow

```
User Action (click, input, etc.)
  → wire/*.js (DOM event handlers, delegates)
    → modals/*.js (UI forms, validation)
      → store.js (CRUD mutations)
        → saveData()
          → storage.js (IndexedDB + localStorage)
        → renderPage()
          → pages/*.js (build HTML string)
            → document.getElementById("pageContent").innerHTML = html
```

### Storage Flow

```
store.js saveData()
  ├─ localStorage.setItem (sync, immediate safety net)
  └─ storage.js adapter.save (async, IndexedDB)

app.js DOMContentLoaded
  └─ storage.js init()
    ├─ IndexedDB open → migrate from localStorage if needed
    └─ resolve data → normalizeData → window.Ledger.DB
```

### UI Flow

```
app.js renderPage()
  ├─ set pageContent.innerHTML via pages/*.js render function
  ├─ wirePageEvents() → wire/*.js for DOM listeners
  ├─ refreshIcons() → lucide.createIcons
  ├─ initCustomDropdowns()
  └─ initDatePickers()

app.js navigateTo(page)
  ├─ update pageTitle/pageSubtitle
  ├─ update globalSearch visibility
  ├─ renderNav
  └─ renderPage
```

### Module Organization

```
/constants.js       — keyword data, category suggestion engine (pure logic)
/utils.js           — entity lookup, balance computation, duplicate detection, formatting
/store.js           — CRUD mutations, default data, data normalization
/modals.js          — modal system (open/close/stack/focus)

/services/
  storage.js        — IndexedDB adapter + localStorage, persist/init

  import-preview.js — unified import preview (grouping, dedup, suggestion, commit)
  recurring.js      — auto-post recurring transactions

/modals/

/components/
```

## AI Development Risks

### Risk 1: Duplicated business logic

**Where:** `filteredTransactions` / `reportFilterTx`, inline duplicate key, learning calls in modal vs import

**Why risky:** An AI contributor changes one copy but not the other → subtle divergence → incorrect filtering in reports or imports.

**Mitigation:** Document all duplication sites. Prefer editing centralized code over forked copies.

### Risk 2: Side-effect coupling

**Where:** Every `store.js` mutation calls `saveData()` + `renderPage()`

**Why risky:** An AI contributor adds a new mutation function or modifies an existing one without realizing it re-renders the entire page. A loop calling `addTransaction()` 100 times triggers 100 re-renders.

**Mitigation:** Document that mutations have side effects. Consider a `batch` flag on mutations for bulk operations.

### Risk 3: Hidden state dependencies

**Where:** `registerFilters`, `reportState`, `overviewState` are mutable global objects read by filter functions

**Why risky:** An AI contributor changes a state object key or default value without checking all consumers.

**Mitigation:** Document the shape and consumers of each state object.

### Risk 4: Complex modal lifecycle

**Where:** `openModal` → `onMount` callback → event binding → close → focus restoration

**Why risky:** An AI contributor adds a new modal or modifies the modal system. Broken focus trap, Escape handler, or backdrop click behavior breaks all forms in the app.

**Mitigation:** The modal system is well-isolated in `modals.js`. Keep all modal HTML generation there or in dedicated modal files.

### Risk 5: Import pipeline coupling

**Where:** CSV parsing → statement parsing → preview → grouping → dedup → category suggestion → batch commit → learning

**Why risky:** An AI contributor changes one stage without understanding the full pipeline. For example, changing the duplicate key in import-preview.js without checking `utils.js` `_dupeKey`.

**Mitigation:** Document the full import lifecycle. Add integration tests for the complete pipeline.

### Risk 6: Stringly-typed entity references

**Where:** `fromType`, `toType` are strings ("account", "person"). `linkRole` is "out" / "in". `type` on transactions is "expense" / "income" / "transfer" / "refund".

**Why risky:** A typo in a string comparison silently fails. `t.type === "expensee"` always returns false, no error thrown.

**Mitigation:** Define constants for all entity types and use them consistently.

## Regression Risks by Module

### If `store.js` changes:

- Every page re-render depends on `saveData()` + `renderPage()`
- Transaction CRUD functions affect all modals, all services
- Category CRUD affects category suggestions duplicate detection
- `replaceAllData` is the backup restore path

### If `modals/tx-modals.js` changes:

- Transaction creation/editing for all 4 types (expense, income, transfer, refund)
- Cross-currency transfer pairs
- Category splits and friend splits
- Refund linking
- Category learning on save

### If `services/import-preview.js` changes:

- CSV import pipeline
- Statement text import
- Duplicate detection during import
- Category suggestion during import
- Batch transaction creation

### If `utils.js` `accountBalance` changes:

- All balance displays (overview, accounts page, register running balance, reports, reconciliation modal)
- Net worth calculation
- Drift detection

### If `services/storage.js` changes:

- Data persistence (fresh install vs returning user)
- localStorage → IndexedDB migration
- Hot-swap data on boot

## Improvement Opportunities

### Opportunity 1: Extract shared filter function (Low effort, Medium payoff)

Consolidate `filteredTransactions` (register.js) and `reportFilterTx` (reports.js) into a single `window.Ledger.filterTransactions(state, types)` in utils.js. Both callers pass their filter state object.

### Opportunity 2: Route bulk delete through deleteTransaction (Very low effort, High payoff)

Change `wire/transactions.js` bulk delete to loop calling `deleteTransaction(id)` instead of raw array filter.

### Opportunity 3: Route recurring auto-post through addTransaction (Low effort, Medium payoff)

Change `services/recurring.js` to call `window.Ledger.addTransaction()` instead of directly pushing to `DB.transactions`.

### Opportunity 4: Extract validation from modal (Medium effort, High payoff)

Move the validation rules from `modals/tx-modals.js` save handler into a standalone `window.Ledger.validateTransaction(data)` function in utils.js. Only extract the validation — leave persistence and learning in the modal.

### Opportunity 5: Align duplicate keys (Low effort, Low payoff)

Change import-preview.js to use `window.Ledger._dupeKey()` instead of its own inline key generation.

### Opportunity 6: Add batch flag to mutations (Medium effort, Medium payoff)

Add an optional `skipRender` parameter (already exists on `addTransaction` and `replaceDebtItemsForTransaction`) to all mutation functions. Use it in batch import.

## Overall Project Health

| Dimension | Rating | Notes |
|---|---|---|
| **Functionality** | Good | All core features work. Edge cases (cross-currency, splits, refunds) are handled. |
| **Architecture** | Fair | Service intent, but business logic leaks into UI code. No formal layering. |
| **Maintainability** | Fair | Single file per concern helps. Duplicate logic and side-effect-heavy mutations hurt. |
| **Scalability** | Fair | Current scale (single-user, local-only) is well-served. Not designed for multi-user or cloud sync. |
| **Readability** | Good | Consistent IIFE pattern, explicit load order, descriptive variable names. |
| **Testability** | Poor | No tests. Side-effect coupling makes testing difficult without refactoring. |
| **AI-friendliness** | Fair | Small files, clear names. But duplicated logic and hidden side effects are traps for AI contributors. |

**Key recommendation for AI contributors:** Before modifying a function that appears in multiple files (filtering, balance computation, duplicate key generation), search for all copies and update them together. Before adding a new mutation, follow the exact pattern in `store.js`. Before modifying a modal, read `modals.js` first to understand the lifecycle.
